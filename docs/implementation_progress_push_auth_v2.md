**Decisiones de diseño donde el plan dejaba algo abierto:**
1. **`RelayServer` NO llama a sus propios endpoints HTTP desde `AuthWorker`.** Siguiendo la nota de nomenclatura del plan y la instrucción explícita de este lote, `RelayServer` expone una API in-process separada de los endpoints HTTP, operando sobre el MISMO `ConcurrentDictionary<string, SessionEntry>`: `RegisterSessionDirect(sessionId, deviceId, nonce, displayCode, attemptNumber, ttl?)` → devuelve el `PushAuthSession` creado; `WaitForResponseDirectAsync(sessionId, ct)` → `Task<PushAuthOutcome>`; `TryGetSession(sessionId, out session)`; `RemoveSession(sessionId)` (para cuando Ruta A/B gana la carrera y hay que cancelar la sesión de Ruta C). Los endpoints HTTP `/api/auth/register` y `/api/auth/wait/{sid}` siguen existiendo (cumplen la tabla literal del plan y permiten el test de humo end-to-end), pero son para el caso de que algo externo los golpee — **Fase 3 debe usar los métodos directos, no HttpClient contra localhost**.
2. **El wire de `/register` NO lleva el nonce.** El JSON de ejemplo del plan (`{session_id, expected_device, jwt}`) no incluye el nonce — es coherente, porque el relay nunca necesita descifrarlo, solo correlacionar `session_id` ↔ `expected_device_id` para el binding de Fisura #7. `RegisterSessionDirect` sí acepta `nonce`/`displayCode` como parámetros porque es conveniente que `AuthWorker` los recupere después vía `TryGetSession` desde la MISMA instancia compartida, pero la ruta HTTP (`RegisterSessionEndpoint`) construye la sesión con `nonce = Array.Empty<byte>()` y `displayCode = ""` — el relay en sí nunca lee esos campos.
3. **Identidad del JWT ("sub"):** el plan es ambiguo — el diagrama de flujo dice `jwt_pc = JWT(sub=pc_id, ...)` pero no existe un concepto de "pc_id" en el resto del sistema (no hay tabla ni GUID para "la PC"). Se resolvió: `sub` es SIEMPRE `DeviceInfo.DeviceId` (el GUID del teléfono emparejado), tanto para el JWT que emite la PC (registrando/esperando una sesión de ESE dispositivo) como el que emite Android (respondiendo como ESE dispositivo) — es la única identidad por la que se puede resolver una `RelayKey` (`RelayKeyDerivation.DeriveRelayKey(device.DeviceKey)`). El delegado `resolveRelayKey: Func<string, byte[]?>` que recibe `RelayServer` en el constructor es quien hace ese lookup; Fase 3 debe pasar algo como `deviceIdStr => { var d = db.Devices.Find(Guid.Parse(deviceIdStr)); return d == null || !d.Enabled ? null : RelayKeyDerivation.DeriveRelayKey(d.DeviceKey); }`.
4. **Transporte del JWT para el endpoint `GET /wait/{sid}`:** el plan muestra un body JSON en un GET, lo cual no es idiomático en Minimal APIs/HTTP. Se implementó `Authorization: Bearer <jwt>` (con fallback a `?jwt=` query string) SOLO para este endpoint; los POST siguen llevando `jwt` dentro del body JSON tal como especifica el plan literalmente. Documentado en el XML doc de `ExtractCredentialsAsync`.
5. **Middleware de rate limiting vs. lógica bespoke:** la tabla de límites tiene 5 filas, pero solo 3 encajan en el modelo de `Microsoft.AspNetCore.RateLimiting` (ventana fija → 429): global (100/min/IP), `/register` (10/min/IP), `/device/token` (5/min/`device_id`, particionado leyendo `ctx.Items` que ya dejó el middleware JWT — por eso el orden del pipeline es JWT ANTES de `UseRateLimiter()`). Las otras 2 filas (`/respond`: 5 intentos/sesión → 403 + invalida sesión; `/wait`: 1 concurrente/sesión → 409) tienen una remediación que NO es un 429 genérico, así que se implementaron como contadores/flags bespoke dentro de `SessionEntry` (`RespondAttempts` con `Interlocked.Increment`, `WaitInProgress` con `Interlocked.CompareExchange`) directamente en los handlers, documentado explícitamente en el comentario sobre `ConfigureRateLimiting`.
6. **Binding de loopback: `127.0.0.1` en vez de `localhost`.** Kestrel no soporta puerto dinámico (`:0`) contra el host especial `"localhost"` (excepción `"Dynamic port binding is not supported when binding to localhost"`) — necesario para que los tests puedan arrancar en un puerto libre asignado por el OS sin colisionar entre sí ni con una instancia real. Se cambió a `http://127.0.0.1:{port}` incondicionalmente (no solo en tests): es exactamente tan loopback-only como `"localhost"`, no es un cambio de postura de seguridad, solo de resolución de dirección. `Protocol.RelayPort = 26821` se usa igual como puerto por defecto en producción.
7. **`UpdateFcmTokenEndpoint`/`FcmTokenUpdateReceived`:** Fase 2 no toca `AppDatabase`, así que el endpoint `/api/device/token` simplemente valida el DTO (JWT ya validó que `device_id` del body coincide con el dueño del JWT) y dispara un evento público `event Action<string, string>? FcmTokenUpdateReceived` (deviceId, nuevoToken) — Fase 8 debe suscribirse a este evento desde `AuthWorker`/donde tenga acceso a `AppDatabase` para persistir `DeviceInfo.FcmToken`/`FcmTokenValid = true`.
8. **Middleware de excepción envuelve también `/health`,** a diferencia del middleware de JWT (que sí lo excluye). El plan dice "excepto para `/health` si aplica" para el middleware de excepción, interpretado aquí como condicional/opcional, no obligatorio — se decidió envolver TODO sin excepción porque no hay downside (un fallo en el propio endpoint de health también debe devolver 500 controlado, no tumbar el proceso).

- **Cómo interactuar con `RelayServer`/sesiones — API exacta:**

**Lo que necesita saber Fase 9 (CP — status messages):**
- Formato exacto en el pipe (sin cambios de este lote, solo documentado con más precisión): cada mensaje `STATUS:...` es una escritura discreta separada al pipe (`PipeServer.WritePipeAsync`, sin delimitador/newline añadido — el pipe se usa en modo mensaje) — es decir, el C++ debe leer cada `ReadFile` como un mensaje `STATUS:` completo, no buscar un `\n` dentro del buffer. ### 🧾 Deuda técnica / hallazgos pendientes para revisión del usuario
1. **Cancelación cruzada de rutas perdedoras no es instantánea** (hallazgo de este lote, Fase 13): `RunAuthRaceAsync` no cancela activamente las rutas que pierden la carrera en el momento en que otra gana — depende del timeout global de 60s y de que cada ruta se limpie a sí misma al resolver. Es una desviación menor de la redacción literal del plan ("el CancellationToken cancela las demás rutas"), de bajo impacto práctico (recursos acotados, sin efectos secundarios duplicados verificados por inspección), pero documentado explícitamente para que el usuario decida si amerita hardening.
2. **Toggle de Push Auth post-pairing no se propaga a Android** (hueco conocido desde Fase 10/12, reconfirmado sin resolver en Fase 13 por estar fuera de su alcance): cambiar `DeviceInfo.PushAuthEnabled` desde la TrayApp después del pairing inicial no actualiza `PairedPc.PushAuthEnabled` en el teléfono. El patrón para cerrarlo ya existe (mensaje de protocolo simétrico a `wingb://token_update`, con fallback al relay) pero no está implementado.
3. **Sin retry/backoff automático si `cloudflared.exe` crashea en runtime** (Fase 4): `TunnelHostedService.OnTunnelDown` solo loguea. No bloqueante para v1 según el propio plan, pero afecta disponibilidad de Ruta B/C hasta el próximo reinicio del Service.
4. **Cero tests automatizados de Named Pipes reales** en todo el repo (`PipeServer`, `AdminPipeServer`) — toda la cobertura de `AuthWorker`/`RelayServer` es sobre HTTP/lógica pura in-process. Si se agrega en el futuro, requeriría un arnés con `NamedPipeServerStreamAcl` real.
